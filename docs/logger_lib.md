# Глава 1. Архитектура ядра логирования (`logger_lib`)

Библиотека `logger_lib` спроектирована как синхронное ядро системы логирования (Часть 1 и Часть 1.5 ТЗ). Она отвечает за создание, фильтрацию, форматирование логов и их последующую отправку в выбранный канал вывода.

---

## 1. Компоненты библиотеки и зоны ответственности

Архитектура библиотеки построена на четком разделении обязанностей между структурами данных, логикой форматирования и каналами ввода-вывода.

### LoggerMessage
Неизменяемый класс, являющийся контейнером для данных одной записи журнала. Хранит три связанных параметра:
* Текст сообщения (`std::string`).
* Уровень важности (`MessageLevel` — перечисление `INFO`, `WARNING`, `ERROR`).
* Временную метку создания (`std::chrono::system_clock::time_point`).

Объект полностью формируется в момент создания и не предоставляет методов для изменения своего состояния (*сеттеров*), что гарантирует защиту от непреднамеренной модификации данных лога.

### OutputInterface
Абстрактный базовый класс, реализующий паттерн **Стратегия**. Он изолирует внутреннее устройство логгера от конкретного физического носителя журнала. Интерфейс предоставляет единственный виртуальный метод для записи данных:
```cpp
virtual std::error_code write(std::string_view message) = 0;
```

Интерфейс имеет две независимые реализации:
1. `OFileInterface` — открывает текстовый файл в режиме добавления (`std::ios::app`) и записывает сформированную строку на диск.
2. `OSocketInterface` — принимает готовый, предварительно подключенный дескриптор сокета (`int`) из внешнего кода. Из класса полностью удалена внутренняя логика создания сетевых соединений (вызовы `::socket`, `::connect`, парсинг IP-адресов). Это снимает ограничения на протокол сетевого уровня, позволяя пользователю библиотеки прозрачно использовать любые типы сокетов (IPv4, IPv6 или локальные UNIX-домены). Такой подход существенно повышает тестируемость класса, позволяя изолированно проверять метод `write` в рамках одного потока с помощью системного вызова `::socketpair()`.


### Logger
Центральный интерфейсный класс библиотеки. Его задачи:
* Хранение текущего атомарного уровня важности по умолчанию.
* Фильтрация входящих сообщений (сообщения с уровнем ниже заданного игнорируются).
* Передача прошедших фильтр объектов во владение связанной стратегии `OutputInterface` через `std::unique_ptr`.

Класс поддерживает динамическое изменение уровня важности по умолчанию в процессе работы приложения.

### LoggerMessageFormater
Вспомогательный класс-фабрика, инкапсулирующий всю логику преобразования форматов. Он содержит два статических метода:
1. `formatToText` — преобразует объект `LoggerMessage` в стандартизированную текстовую строку вида `[ YYYY-MM-DD HH:MM:SS ] [ LEVEL ] message.\n`.
2. `formatToLoggerMessage` — выполняет обратную десериализацию текстовой строки из сокета обратно в объект `LoggerMessage` с посимвольным разбором префиксов и валидацией маски времени. При ошибке парсинга безопасно возвращает `std::nullopt`.

> **Примечание по конфигурации:** Вывод времени и его парсинг являются гибко настраиваемыми на этапе компиляции. Внутри класса определены константы `timeMask` (задающая маску отображения даты/времени, по умолчанию `"%Y-%m-%d %H:%M:%S"`) и `timeCoff` (задающая жесткое смещение относительно Гринвича в секундах, по умолчанию `10800` для принудительного перехода на Московское время UTC+3 независимо от системных настроек окружения).

## 2. Обработка ошибок и noexcept-подход

В соответствии с требованиями технического задания, в библиотеке полностью исключено использование механизма исключений для обработки нештатных ситуаций бизнес-логики.

Все потенциально опасные операции (отсутствие доступа к файлу, сбой системного вызова `::send`) обрабатываются с помощью стандартного механизма **`std::error_code`**:

* Для внутренних ошибок библиотеки создано кастомное перечисление `LoggerError` и зарегистрирована выделенная категория ошибок `std::error_category`.
* Системные сбои сетевого уровня (например, возврат отрицательного значения из `::send`) транслируют код `errno` напрямую в системную категорию `std::generic_category()`.

Это обеспечивает более производительную работу системы и гарантирует полную совместимость со стандартным системным API (таким как `errno` и другими стандартными кодами ошибок) без накладных расходов.
