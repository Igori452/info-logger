# Подробная техническая документация проекта

Данный раздел содержит глубокий технический анализ архитектурных решений, структуры данных и сетевых алгоритмов, примененных при реализации всех трех частей технического задания.

---

### [Глава 1. Архитектура ядра логирования (`logger_lib`)](logger_lib.md)
Подробный разбор ядра системы логирования (Часть 1 и Часть 1.5). Рассмотрены ключевые классы (`Logger`, `LoggerMessage`) и реализация паттерна **Стратегия** через интерфейс вывода `OutputInterface`. Описан noexcept-подход, полностью исключающий `exceptions` из бизнес-логики в пользу `std::error_code` с кастомной категорией ошибок.

### [Глава 2. Многопоточное демонстрационное приложение (`app`)](app.md)
Анализ асинхронного слоя управления потоками (Часть 2). Описана реализация классического паттерна **Producer-Consumer** на базе потокобезопасной очереди задач, синхронизированной через `std::mutex` и `std::condition_variable`. Рассмотрен жизненный цикл фонового рабочего потока (`ThreadManager`), а также механизмы гарантированной корректной остановки приложения.

### [Глава 3. Сервер сбора сетевой статистики (`socket_app`)](socket_app.md)
Детальный разбор архитектуры консольного сервера статистики (Дополнительная Часть 3):
* **Сетевой уровень (`SocketReceiver`)**: Чтение данных из сокета. Реализован цикл `while` с флагом `MSG_DONTWAIT`, который полностью вычитывает входящий буфер операционной системы за один вызов метода. Использование фиксированного буфера на 4 КБ исключает динамические аллокации памяти при чтении из сети и защищает поток от блокировки.
* **Уровень бизнес-логики (`MessageStatistics`)**: Расчет следующих метрик: общее количество обработанных сообщений, количество сообщений по уровням важности, количество сообщений за последний час, а также минимальная, максимальная и средняя длина сообщений.
* **Уровень оркестрации (`ServerRunner`)**: Инкапсуляция всей логики Части 3 в единый ранер. Управляет выводом логов в поток `std::ostream&` и отслеживает триггеры выдачи статистики: после каждого $N$-го сообщения, а также по таймауту неактивности $T$. Для триггера таймаута реализована проверка через `hasChanged()`, что исключает повторный вывод неизменившихся данных.


### [Глава 4. Стратегия тестирования и верификация системы (`tests`)](testing.md)
Описание комплексной стратегии тестирования всего программного комплекса без использования сторонних фреймворков, построенной строго на возможностях стандарта C++17 и CTest:
* **Тестирование ядра (`logger_lib`)**: Юнит-тесты логики фильтрации, форматирования строк и round-trip десериализации текстового представления лога обратно в объект `LoggerMessage` с проверкой граничных условий и точности `time_point`.
* **Тестирование многопоточности (`app`)**: Проверка потокобезопасной очереди, штатного завершения работы потоков и отсутствия data races.
* **Интеграционное тестирование сети (`socket_app`)**: Использование системного вызова `::socketpair(AF_UNIX)` для сквозной имитации работы сетевых буферов ОС Linux. Детальная верификация логики фрагментации пакетов и обработки таймаутов.
