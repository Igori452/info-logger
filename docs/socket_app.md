# Глава 3. Сервер сбора сетевой статистики (`socket_app`)

Приложение `socket_app` спроектировано как консольный сервер (Дополнительная Часть 3 ТЗ) для приема текстовых сообщений из сети, отправляемых библиотекой логирования через сокет (Часть 1.5). Архитектура сервера построена на строгом разделении зон ответственности между сетевым уровнем, модулем расчета метрик и оркестратором приложения.

---

## 1. Компоненты сервера и зоны ответственности

### Сетевой уровень (`SocketReceiver`)
Класс отвечает за низкоуровневое чтение данных из сокета и накопление их во внутреннем строковом буфере памяти `streamBuffer`.
* **Метод `waitData(T)`**: Использует системный вызов `::poll` для блокирующего ожидания событий в сокете с ограничением по времени в $T$ секунд. Возвращает статус операции в виде `std::error_code`.
* **Метод `readFromNetwork()`**: Реализует неблокирующее чтение накопленных операционной системой байт. Внутри метода используется фиксированный буфер `char msgBuffer[4096]` и цикл `while`, вызывающий функцию `::recv` с флагом `MSG_DONTWAIT`. Цикл работает до тех пор, пока `::recv` возвращает значение больше нуля. Это позволяет полностью вычитать сетевой буфер ОС за один вызов метода без накладных расходов на динамическое выделение памяти на каждый пакет и защищает поток от зависания, если клиент отправил строку не до конца.
* **Метод `getNextMessage(separator)`**: Выполняет линейный поиск символа-разделителя (в данном случае `\n`) во внутреннем буфере `streamBuffer`. При его обнаружении метод отрезает готовую строку лога, удаляет её из буфера накопителя и безопасно возвращает в виде `std::optional<std::string>`.

### Уровень бизнес-логики (`MessageStatistics`)
Класс аккумулирует в себе все агрегируемые метрики логов и изолирован от сетевых вызовов. При каждом вызове метода `setData()` выполняется перерасчет следующих показателей:
1. **Общее количество сообщений**: Простой инкремент счетчика `totalMessages`.
2. **Распределение по уровням важности**: Подсчет ведется внутри контейнера `std::map<MessageLevel, size_t>`.
3. **Скользящее часовое окно**: Каждая временная метка `time_point` сохраняется в динамический массив `std::vector<TimePoint>`. При обработке нового лога с помощью идиомы *Erase-Remove* и алгоритма `std::remove_if` из вектора удаляются все метки, которые старше, чем `текущее_время - 1 час`. Актуальный размер вектора всегда равен честному числу сообщений за последние 60 минут.
4. **Статистика длин сообщений**: Рассчитываются минимальная (`minLenMessage`), максимальная (`maxLenMessage`) длины. Также рассчитывается среднее значение длины (`averageLenMessage`) по формуле, исключающей необходимость хранить длины всех прошлых сообщений лога.

Класс также управляет флагом изменений `dataChanged`, который сбрасывается в `false` при вызове метода `hasChanged()`.

### Уровень оркестрации (ServerRunner)
Пространство имен `ServerRunner` содержит функцию `run()`, которая является оркестратором бизнес-логики Части 3. Функция принимает на вход голый дескриптор сокета (`int`), параметры триггеров $T$ и $N$, а также ссылку на абстрактный поток вывода `std::ostream& os`.
Оркестратор координирует работу ресивера и статистики в бесконечном цикле:
* Передает вычитанные сетевые строки в фабрику `LoggerMessageFormater::formatToLoggerMessage()` для десериализации текстового представления обратно в `LoggerMessage`.
* Выводит принятый сырой лог в поток `os`.
* **Триггер N**: Отслеживает количество успешно обработанных сообщений лога после последней выдачи. Как только счетчик достигает заданного порога $N$, вызывает внешнюю чистую функцию `printStatistic()` для вывода таблицы метрик в поток `os`.
* **Триггер T**: Если системный `::poll` возвращает `0` (таймаут неактивности сокета), ранер проверяет состояние метрик через метод `msgStat.hasChanged()`. Вывод таблицы статистики по таймауту наступает строго при условии, что с момента прошлой выдачи сервер успел обработать новые уникальные данные, что полностью предотвращает спам пустых отчетов в консоль при молчании клиента.
