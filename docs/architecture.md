# Глава 1. Архитектура и дизайн системы

Архитектура проекта строго разделена на два независимых слоя: **синхронный слой логирования** (компилируемый в библиотеку `logger_lib`) и **асинхронный слой управления потоками** (компилируемый в составе приложения `app_core`). 

Такое разделение гарантирует, что библиотека остается легковесной и может использоваться в любых контекстах, а многопоточная логика изолирована в приложении.

---

## 1. Синхронное ядро логгера (`logger_lib`)

### Общая структура файлов ядра
Синхронное ядро полностью изолировано в рамках библиотеки `logger_lib` и имеет следующую структуру:
* `include/logger_lib/LoggerMessage.hpp` — объявление структуры сообщения, возможных уровней и класса для форматирования сообщений.
* `include/logger_lib/OutputInterface.hpp` — абстракция стратегии вывода.
* `include/logger_lib/Logger.hpp` — основной класс логгера, управляющий фильтрацией.
* `include/logger_lib/ErrorCodes.hpp` — кастомные коды ошибок на базе `std::error_code`.
* Папка `src/` содержит соответствующие `.cpp` файлы реализации.

### Класс `Logger`
Класс `Logger` является центральным управляющим звеном синхронного ядра библиотеки. Он инкапсулирует бизнес-логику фильтрации сообщений и координирует процесс записи. Его устройство опирается на следующие принципы:

* **Управление уровнем важности (Фильтрация)**: При инициализации класс принимает уровень важности по умолчанию (`defaultLevel`). Метод `log(const LoggerMessage&)` перед отправкой сообщения сравнивает его уровень с текущим базовым уровнем логгера. Если важность сообщения ниже установленного порога, логгер возвращает некритический статус ( `LoggerError::FILTERED`), завершая обработку.
* **Слабая связанность и полиморфизм**: `Logger` не привязан к конкретной реализации файлового вывода. Он владеет указателем на абстрактный интерфейс `OutputInterface`. В момент записи логгер делегирует задачу физического вывода подключенной стратегии (файл или сокет), передавая туда уже готовую, отформатированную строку. Такой подход делает класс полностью независимым от деталей низкоуровневого API.

### Класс `LoggerMessage`
В соответствии с требованиями ТЗ, в журнале должна сохраняться информация о тексте, уровне важности и времени получения сообщения. Для этого спроектирован неизменяемый класс `LoggerMessage`:

* **RAII и фиксация времени**: Конструктор по умолчанию удален (`= delete`). Объект может быть создан только при явной передаче текста сообщения и его уровня. Точка времени (`timeCreation`) фиксируется **автоматически** прямо в момент вызова конструктора с помощью `std::chrono::system_clock::time_point`. Это гарантирует абсолютную точность метки времени получения сообщения.
* **Инкапсуляция**: Все поля класса скрыты в `private`. Доступ к данным предоставляется через константные геттеры, что исключает случайное изменение содержимого сообщения в процессе его перемещения по очередям приложения.

### Вынос логики форматирования (`LoggerMessageFormater`)
Для соблюдения принципа единственной ответственности логика преобразования объекта сообщения в текстовую строку вынесена из самого класса данных в специализированный класс фабрику - `LoggerMessageFormater`.

Класс предоставляет статический метод `formatToText`, который переводит системное время в человекочитаемый вид по маске `[ YYYY-MM-DD HH:MM:SS ]`, выравнивает теги уровней важности по ширине для сохранения табличной структуры лога и добавляет финальную точку к сообщению. Это позволяет легко изменять формат вывода (например, переключиться на JSON) без изменения структуры хранения данных `LoggerMessage`.

### Абстракция вывода (`OutputInterface`)
Для выполнения требования ТЗ о возможности логирования как в файл, так и в сокет, применен паттерн **Стратегия**:
* `OutputInterface` — виртуальный базовый класс, предоставляющий метод `write(std::string_view)`.
* `OFileInterface` — конкретная реализация для работы с `std::ofstream`.
* Возможность добавить взаимодействие с любым сервисом для вывода сообщений (сокет/UI и тд)

### Класс `ErrorCodes`
Согласно требованиям ТЗ, исключения в бизнес-логике запрещены. Все потенциально опасные операции (открытие файла, сбои записи) обрабатываются через механизм `std::error_code`. Это позволяет возвращать детальные системные ошибки, не нарушая стабильности потоков и не прерывая работу всей системы.

Интеграция перечисления `LoggerError` в стандартную подсистему `<system_error>` выполнена с помощью перегрузки функции `make_error_code`, которая связывает числовые значения ошибок с синглтоном нашей категории `LoggerCategory`. Это позволяет объектам `std::error_code` возвращать текстовые описания ошибок через метод `message()`.

#### Таблица кодов ошибок системы логирования

| Имя константы (Enum) | Числовое значение | Тип ошибки | Текстовое описание (`message()`) | Влияние на жизненный цикл программы |
| :--- | :---: | :--- | :--- | :--- |
| **`SUCCESS`** | `0` | Информационный | *Успешное выполнение* | Операция завершена штатно, программа продолжает работу. |
| **`FILTERED`** | `1` | Некритический | *Сообщение отфильтровано* | Важность сообщения ниже текущего порога логгера. Запись пропущена, программа продолжает работу. |
| **`FILE_NOT_OPEN`** | `2` | **Критический** | *Не удается открыть файл по указанному пути* | Поток `std::ofstream` не смог открыться (неверные путь/права). |
| **`WRITE_FAILED`** | `3` | **Критический** | *Не удалось записать данные в поток* | Произошел сбой при физической записи на диск или сбросе буфера. |

## 2. Асинхронный слой приложения (`app`)

### Общая структура файлов приложения
* `ThreadManager/ThreadManager.hpp` — объявление класса менеджера потоков и потокобезопасной очереди сообщений.
* `main_app.cpp` — исполняемый файл консольного интерфейса (поток чтения `std::cin`).

Асинхронность ввода и записи реализована в классе `ThreadManager` на основе классического паттерна **Producer-Consumer**.

### Принципы работы многопоточности:
1. **Поток-Продюсер (UI thread)**: считывает данные из `std::cin`, вызывает `ThreadManager::push()`. Метод захватывает `std::lock_guard<std::mutex>`, мгновенно помещает сообщение в `std::queue` и будит рабочий поток через `condition_variable::notify_one()`. UI-поток никогда не блокируется операциями записи.
2. **Поток-Консьюмер (Фоновый поток логгера)**: ожидает уведомления в методе `pop()`. При пробуждении он извлекает сообщение, вызывает синхронный `Logger::log()` и снова засыпает, если очередь пуста.
3. **Безопасная остановка и обработка критических ошибок**: 
   * **Штатное завершение**: При отправке пустой строки UI-поток вызывает метод `stop()`, который выставляет флаг `stopFlag = true` и будит фоновый поток через `workerFlag.notify_all()`. Рабочий поток гарантированно дочитывает все оставшиеся в очереди сообщения, записывает их на диск и только после этого завершает свой цикл работы.
   * **Аварийная остановка**: Если во время записи сообщения фоновый поток сталкивается с критической системной ошибкой (например, `LoggerError::FILE_NOT_OPEN`), он вызывает метод `ThreadManager::setError(ec)`. Внутри метода проверяется пришедший код ошибки: если это не успех и не фильтрация, менеджер **автоматически взводит флаг `stopFlag = true`**. Это мгновенно переводит систему в аварийный режим, предотвращая дальнейшее накопление сообщений в очереди, которые всё равно не могут быть записаны. UI-поток обнаруживает взведенный флаг на следующей итерации цикла ввода, корректно завершает работу программы и возвращает операционной системе код `1`.
